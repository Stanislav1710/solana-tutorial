# Урок 16 — Комиссии (Fees) и оптимизация расходов

---

## 1. Введение

Каждая транзакция в Solana требует оплаты комиссии.
Эта комиссия идёт валидаторам за выполнение работы: проверку подписей, выполнение инструкций, хранение данных и запись транзакции в блок.

В отличие от некоторых сетей, в Solana:

* комиссия **очень маленькая** (обычно доли цента);
* комиссия **фиксируется заранее** — её можно узнать перед отправкой;
* комиссия **не зависит от нагрузки сети** (нет «газовой гонки» как в Ethereum);
* комиссия зависит **только от размера транзакции и сложности инструкций**.

В этом уроке мы разберём:

1. из чего состоит комиссия;
2. как узнать комиссию заранее;
3. как работать с RPC для расчёта fees;
4. минималистичный пример расчёта комиссии перед отправкой;
5. как уменьшать комиссию в реальных проектах.

---

## 2. Что такое комиссия в Solana

Комиссия = **стоимость проверки подписи + стоимость размера сообщения + стоимость инструкций.**

Комиссия выражается в **лампортах**.

Примерная структура:

```
Комиссия =
  базовая стоимость проверки подписи
+ стоимость размера транзакции (количество байтов)
+ стоимость выполнения инструкций
```

Сеть сама вычисляет точное значение.
Наша задача — узнать его через RPC **до отправки транзакции**.

---

## 3. Где хранится информация о комиссии

Есть два основных RPC-метода:

1. `get_fee_for_message(message)`
   → вычисляет точную комиссию для **конкретного Message**.

2. `get_latest_blockhash()`
   → возвращает поле `fee_calculator` (в старых RPC), но Solana постепенно уходит от него.
   Поэтому **основной способ — считать через Message**.

---

## 4. Почему считаем комиссию до отправки

Это важно для:

* проверки, хватит ли средств на комиссии;
* отображения пользователю (кошельки всегда так делают);
* массовых выплат и роботов;
* расчётов и аналитики;
* экономии при больших батчах транзакций.

---

## 5. Минимальный пример: расчёт комиссии (Python)

В этом примере мы:

1. загружаем `course_wallet.bin`;
2. создаём стандартную инструкцию `transfer` (Урок 14);
3. создаём Message;
4. вычисляем комиссию через RPC;
5. отправляем транзакцию и сверяем фактическую комиссию.

Используем код из [`examples/Python/L16-Fee_estimation.py`](../examples/Python/L16-Fee_estimation.py):

```python
from solana.rpc.api import Client
from solders.keypair import Keypair
from solders.system_program import transfer, TransferParams
from solders.message import Message
from solders.transaction import Transaction

DEVNET = "https://api.devnet.solana.com"
client = Client(DEVNET)

# 1. Загрузить учебный кошелёк
with open("course_wallet.bin", "rb") as f:
    kp = Keypair.from_bytes(f.read())

pub = kp.pubkey()
print("Адрес:", pub)

# 2. Готовим инструкцию перевода самому себе
ix = transfer(TransferParams(
    from_pubkey=pub,
    to_pubkey=pub,
    lamports=1
))

# 3. Получаем блокхеш
latest = client.get_latest_blockhash().value
blockhash = latest.blockhash

# 4. Создаём Message
msg = Message.new_with_blockhash([ix], pub, blockhash)

# 5. Оцениваем комиссию
fee = client.get_fee_for_message(msg).value
print("Оценка комиссии:", fee, "lamports")

# 6. Собираем и подписываем транзакцию
tx = Transaction([kp], msg, blockhash)
tx.partial_sign([kp], blockhash)

# 7. Отправляем
sig = client.send_transaction(tx).value
print("Сигнатура:", sig)

# 8. Проверяем статус
st = client.get_signature_statuses([sig]).value[0]
print("Результат:", st)
```

## 6. Как это работает внутри

### 6.1. Message → Fee calculation

RPC получает ваш Message и выполняет:

1. сериализацию байтов;
2. оценку стоимости подписи;
3. оценку стоимости каждой инструкции;
4. суммирование результата.

Затем RPC возвращает точное количество лампортов.

---

## 7. Почему комиссия может меняться

Комиссия зависит от:

* количества аккаунтов в транзакции;
* количества инструкций;
* размера `Message` (байты);
* количества подписей.

Если:

* добавить вторую инструкцию → комиссия увеличится;
* добавить второго подписанта → комиссия увеличится;
* поместить inode данных → комиссия увеличится.

Если транзакция небольшая и простая (как в Уроке 14), комиссия очень маленькая.

---

## 8. Типовые значения комиссии

Для обычного перевода SOL:

* комиссия ≈ **5 000–10 000 лампортов**
  (это примерно $0.00005 — $0.0001 при ~20–30$ за SOL).

Для сложных транзакций:

* с PDA, Borsh, множественными инструкциями → комиссия растёт;
* но всё равно остаётся значительно ниже, чем в сетях с газовой моделью.

---

## 9. Оптимизация комиссий

Чтобы тратить меньше:

### 9.1. Объединяйте инструкции в одну транзакцию

Вместо:

* 5 транзакций × 10 000 лампортов
  делайте:

* 1 транзакцию с 5 инструкциями × 12 000 лампортов

Экономия огромная.

---

### 9.2. Минимизируйте объём данных

* меньше аккаунтов → меньше комиссий;
* меньше data → меньше байтов;
* короткие PDA → меньше сериализованных данных.

---

### 9.3. Повторное использование PDA

**PDA (Program Derived Address)** — это «адрес, который создаёт программа сама для себя», чтобы хранить свои данные.
У такого адреса **нет приватного ключа**, поэтому пользователь не может им владеть или подписывать за него транзакции. PDA вычисляется по специальной формуле из набора seed-ов, а подпись за него делает сама программа.

Подробное изучение PDA будет в **Уроке 27 — «PDA: концепт, seeds и почему PDA нельзя контролировать приватным ключом»**.

Почему это относится к комиссиям:

* создание нового PDA требует выделения памяти и перевода lamports, что увеличивает комиссию;
* если PDA уже создан один раз, повторное использование снижает комиссию в дальнейших операциях;
* большие on-chain проекты экономят значительные суммы, правильно организовав хранение данных в одном PDA, а не создавая новые каждый раз.

---

### 9.4. Правильный расчёт перед отправкой

Используйте `get_fee_for_message()` перед отправкой.
Так поступают все кошельки.

## 11. Ключевые выводы

* Комиссия в Solana низкая и стабильная.
* Комиссия зависит только от структуры транзакции, а не от нагрузки сети.
* `get_fee_for_message()` позволяет точно узнать комиссию заранее.
* Оптимизация транзакций снижает расходы в десятки раз при массовых операциях.
* Правильная работа с комиссиями — основа надёжных dApp и бэкендов.
