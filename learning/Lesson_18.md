# Урок 18 — Частичная подпись (Partial Signing) и мультиподписи

---

## 1. Введение

В предыдущем уроке мы научились объединять несколько инструкций в одну транзакцию (Урок 17).
Теперь мы рассмотрим важный механизм Solana:

**частичная подпись (partial sign)**
и
**мультиподпись (multi-signature)**.

Это фундаментальная часть безопасности.
Некоторые транзакции требуют не одной подписи, а сразу нескольких — от разных аккаунтов.
Solana позволяет подписывать транзакцию не сразу всеми участниками, а **по очереди**, передавая её между владельцами ключей.

Мы разберём:

1. зачем нужны частичные подписи;
2. как база Solana определяет, какие подписи обязательны;
3. что происходит при сборке транзакции;
4. минимальный пример с двумя Keypair;
5. наглядную схему процесса;
6. типичные ошибки и как их избежать.

---

## 2. Почему частичные подписи необходимы

В Solana каждая инструкция требует **конкретных подписантов**.
Это определяется структурой инструкций (`AccountMeta.is_signer=True`).

Примеры, где требуется несколько подписей:

* перевод с multisig-кошелька (например, 2-из-3 владельцев должны подписать);
* изменение владельца PDA-счёта (если и программа, и пользователь участвуют);
* перемещения токенов, если authority принадлежит двум участникам;
* dApp, в котором транзакция должна быть подписана двумя разными пользователями.

Если транзакция требует 3 подписи, а подписали только 2 → она отклоняется.

---

## 3. Как Solana понимает, кто должен подписывать

Каждая инструкция содержит `AccountMeta`:

* `pubkey`
* `is_signer`
* `is_writable`

Если хотя бы одному из аккаунтов указано:

```
is_signer = True
```

то приватный ключ этого аккаунта должен подписать транзакцию.

Если подписи нет → ошибка при отправке:

```
missing required signature
```

---

## 4. Что такое частичная подпись

Одна и та же транзакция может быть подписана **по частям**, разными людьми.

Пример:

1. Пользователь A создаёт транзакцию, подписывает свою часть.
2. Отправляет (например, через API/файл/QR) транзакцию пользователю B.
3. Пользователь B подписывает свою часть.
4. Отправляет транзакцию в сеть.

Это позволяет безопасно выполнять операции, где:

* подписанты находятся в разных местах;
* нельзя передавать приватные ключи;
* пользователь использует аппаратный кошелёк;
* приложение собирает транзакции в бекенде.

---

## 5. Как это выглядит технически

Схема:

```
            [ Message ]
                 │
       ┌─────────┼─────────┐
       ▼                   ▼
partial_sign(A)     partial_sign(B)
       │                   │
       └─────────┬─────────┘
                 ▼
          [ Transaction ]
                 │
                 ▼
         send_transaction()
```

Solana хранит подписи в массиве Signatures:

```
signatures = [sig_A, sig_B, None, None...]
```

После того как все обязательные подписи заполнены, транзакцию можно отправлять.

---

## 6. Пример: три подписи для одной транзакции

В этом примере:

1. мы используем course_wallet.bin как единственного плательщика комиссии;
2. этот же кошелёк отправляет и получает 1 лампорт (перевод самому себе);
3. создаём два дополнительных ключа A и B, которые не имеют баланса — они только подписанты;
4. затем подписываем всеми необходимыми ключами;
5. отправим в сеть.

Используем код из [`examples/Python/L18-Partial_Signing.py`](../examples/Python/L18-Partial_Signing.py):

```python
from solana.rpc.api import Client
from solders.keypair import Keypair
from solders.instruction import Instruction, AccountMeta
from solders.message import Message
from solders.transaction import Transaction
from solders.system_program import transfer, TransferParams

DEVNET = "https://api.devnet.solana.com"
client = Client(DEVNET)

# 1. Загружаем основной учебный кошелёк (payer + from_pubkey)
with open("course_wallet.bin", "rb") as f:
    main = Keypair.from_bytes(f.read())

main_pub = main.pubkey()
print("Основной адрес:", main_pub)

# 2. Создаём двух дополнительных подписантов (баланс им не нужен)
A = Keypair()
B = Keypair()

print("Доп. подписант A:", A.pubkey())
print("Доп. подписант B:", B.pubkey())

# 3. Базовая инструкция перевода: main -> main (перевод самому себе)
base_ix = transfer(TransferParams(
    from_pubkey=main_pub,
    to_pubkey=main_pub,
    lamports=1
))

# 4. Модифицируем список аккаунтов:
#    - основной подписант (main)
#    - добавляем A и B как дополнительных подписантов
accounts = list(base_ix.accounts)
accounts.append(AccountMeta(pubkey=A.pubkey(), is_signer=True, is_writable=False))
accounts.append(AccountMeta(pubkey=B.pubkey(), is_signer=True, is_writable=False))

ix = Instruction(
    program_id=base_ix.program_id,
    accounts=accounts,
    data=base_ix.data
)

# 5. Получаем blockhash
latest = client.get_latest_blockhash().value
blockhash = latest.blockhash

# 6. Формируем Message
msg = Message.new_with_blockhash([ix], main_pub, blockhash)

# 7. Создаём транзакцию без подписей
tx = Transaction([], msg, blockhash)

# 8. Частичная подпись основного кошелька
tx.partial_sign([main], blockhash)

# 9. Частичная подпись A и B
tx.partial_sign([A], blockhash)
tx.partial_sign([B], blockhash)

# 10. Отправляем транзакцию в сеть
sig = client.send_transaction(tx).value
print("Сигнатура:", sig)

# 11. Проверяем статус
status = client.get_signature_statuses([sig]).value[0]
print("Статус:", status)

```

## 7. Разбор кода

### 7.1. Почему A и B могут быть без баланса

Они не являются:

* отправителями SOL,
* получателями,
* плательщиками комиссии.

Они только подписывают транзакцию как обязательные участники.

**Подпись не требует лампортов.**

---

### 7.2. Все подписи добавлены в один и тот же объект `tx`

Каждый вызов:

```
tx.partial_sign([...])
```

добавляет новую подпись и не удаляет предыдущие.

---

### 7.3. Отправка происходит только после всех подпечатей

Пока все `is_signer=True` участники не подписали — отправка невозможна.

---

### 7.4. Порядок подписания не важен

Можно подписывать в произвольном порядке:

* сначала B, потом main, потом A — всё будет работать.

---


## 8. Где реально используются частичные подписи

| Сценарий                     | Зачем нужна                                    |
| ---------------------------- | ---------------------------------------------- |
| **Multisig кошельки**        | Требуется несколько владельцев                 |
| **Cross-program operations** | Несколько владельцев PDA/ATA                   |
| **DAO/Governance**           | Комитеты подписывают решения                   |
| **DEX/Trading боты**         | Backend подписывает часть, пользователь — свою |
| **Аппаратные кошельки**      | Подпись приходит из Ledger/Trezor              |

Частичная подпись — это стандартный механизм, а не «исключение».

---

## 9. Типичные ошибки

| Ошибка                       | Причина                                    | Решение                             |
| ---------------------------- | ------------------------------------------ | ----------------------------------- |
| `missing required signature` | не все `is_signer` подписали               | подписать каждым нужным Keypair     |
| `InvalidSignature`           | подпись сделана для другого blockhash      | собрать Message заново              |
| `AccountNotFound`            | подписант не является владельцем аккаунта  | проверить владельцев/роли           |
| `ReadonlyLamportChange`      | пытаемся менять lamports без `is_writable` | проверить `AccountMeta.is_writable` |

---

## 11. Ключевые выводы

* В Solana транзакция может требовать несколько подписантов.
* Подписи можно добавлять по очереди — это называется частичной подписью.
* Механизм partial_sign позволяет безопасно распределить ответственность.
* Без всех обязательных подписей транзакция отклоняется.
* Partial signing — основа multisig, DAO и сложных dApp.
