# Урок 15 — Commitment levels: processed / confirmed / finalized

---

## 1. Введение

Каждый раз, когда мы отправляем транзакцию или читаем данные через RPC, возникает вопрос:

**«Насколько надёжные данные я получаю сейчас?»**

В сети Solana блоки создаются очень быстро, а транзакции обрабатываются параллельно.
Поэтому у каждого RPC-запроса есть параметр **commitment** — это требование к уровню «надёжности» данных.

В этом уроке мы разберём:

1. что такое commitment levels;
2. зачем они нужны;
3. чем отличаются `processed`, `confirmed` и `finalized`;
4. когда и какой уровень использовать;
5. как работать с commitment через Python (`solana` и `solders`);
6. как проверять подтверждение транзакций.

Урок логически продолжает Урок 14, где мы впервые отправили настоящую транзакцию.

---

## 2. Почему нужны уровни подтверждения

Solana — это высокопроизводительная сеть.
В ней транзакции проходят несколько стадий:

1. **Попала в локальный узел** → обработана локально.
2. **Попала в недавний блок** → подтверждена большинством валидаторов.
3. **Закреплена супермажорити валидаторов** → изменение необратимо.

Каждый этап даёт разный уровень доверия.

Commitment — это способ сказать RPC-узлу:

> «Дай мне данные, которые доступны на уровне X надёжности».

---

## 3. Три уровня commitment

Solana использует три основных уровня:

### 3.1. `processed` — минимальная надёжность

Это означает:

* узел уже **видел** транзакцию или изменение;
* он обработал их локально;
* **но** другие узлы сети могут быть ещё не в курсе.

Подходит для:

* быстрых UI-обновлений;
* отслеживания прогресса транзакции;
* отображения «примерного» состояния.

Не подходит для:

* критических расчётов;
* финального отображения баланса.

---

### 3.2. `confirmed` — средняя надёжность

Это означает:

* транзакция попала в блок;
* блок уже **подтверждён большинством валидаторов**;
* откат маловероятен.

Используется в:

* большинстве dApp-интерфейсов;
* отображении актуального состояния;
* проверке недавних операций.

---

### 3.3. `finalized` — максимальная надёжность

Это означает:

* блок закреплён супермажорити валидаторов;
* изменение считается окончательным;
* откат практически невозможен.

Рекомендуется для:

* бухгалтерии, отчётов, аудита;
* операций с высокой стоимостью;
* логирования в базе данных.

---

## 4. Схема уровней подтверждения

```
Транзакция →
    ├── processed   (узел видел и обработал)
    ├── confirmed   (в блоке, блок подтверждён большинством)
    └── finalized   (блок необратим, супермажорити закрепило)
```

---

## 5. Commitment в RPC-запросах

Любой запрос может принимать опцию `commitment`.

Пример:

```python
client.get_balance(pubkey, commitment=Commitment("finalized"))
```

или

```python
client.get_account_info(pubkey, commitment=Commitment("confirmed"))
```

Если не указать явно — используется дефолтный уровень RPC-узла (обычно `finalized`).

---

## 6. Минимальный пример (Python)

В примере ниже мы получим:

* текущий слот с разными уровнями commitment;
* баланс одного и того же аккаунта в разных состояниях.

Используем код из [`examples/Python/L15-Commitment_levels.py`](../examples/Python/L15-Commitment_levels.py):

```python
from solana.rpc.api import Client, Commitment
from solders.solders import Keypair


client = Client("https://api.devnet.solana.com")

with open("course_wallet.bin", "rb") as f:
    wallet = Keypair.from_bytes(f.read())

pubkey = wallet.pubkey()

# 1. Сравнение слотов
slot_processed = client.get_slot(commitment=Commitment("processed")).value
slot_confirmed = client.get_slot(commitment=Commitment("confirmed")).value
slot_finalized = client.get_slot(commitment=Commitment("finalized")).value

print("Слот processed:", slot_processed)
print("Слот confirmed:", slot_confirmed)
print("Слот finalized:", slot_finalized)

# 2. Баланс одного аккаунта
b1 = client.get_balance(pubkey, commitment=Commitment("processed")).value
b2 = client.get_balance(pubkey, commitment=Commitment("confirmed")).value
b3 = client.get_balance(pubkey, commitment=Commitment("finalized")).value

print("Баланс (processed):", b1)
print("Баланс (confirmed):", b2)
print("Баланс (finalized):", b3)
```

## 7. Commitment и подтверждение транзакций

После отправки транзакции (см. Урок 14) мы получаем `Signature`.
Чтобы узнать, прошла ли она успешно, используем:

```python
client.get_signature_statuses([sig])
```

Ответ содержит:

* `confirmations`
* `err`
* `confirmation_status` (`processed`, `confirmed`, `finalized`)

### Пример:

```
confirmation_status: TransactionConfirmationStatus.Finalized
```

Это означает, что транзакция полностью завершена.

---

## 8. Когда какой level использовать (практические рекомендации)

| Уровень       | Когда применять                                   |
| ------------- | ------------------------------------------------- |
| **processed** | быстрые UI обновления, индикаторы выполнения      |
| **confirmed** | стандартное отображение состояния в приложении    |
| **finalized** | критические данные, бухгалтерия, backend-фиксация |

---

## 9. Частые ошибки и их причины

| Ошибка                              | Причина                                                                 | Решение                                           |
| ----------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------- |
| Баланс «не обновился»               | запрос был с commitment `finalized`, а транзакция ещё не финализирована | использовать временно `processed` или `confirmed` |
| Статус транзакции `None`            | транзакция слишком свежая или RPC отдал быстрый снимок                  | повторить запрос, дождаться `confirmed`           |
| Разные RPC показывают разные данные | разные уровни commitment                                                | указать commitment явно                           |

---

## 11. Ключевые выводы

* Commitment — это степень надёжности данных, которые мы просим у RPC.
* `processed` — быстрый, но самый слабый уровень.
* `confirmed` — сбалансированный и чаще всего используемый.
* `finalized` — гарантированная неизменяемость данных.
* Для проверки транзакций используем `get_signature_statuses`.
* Программы и кошельки в Solana всегда выбирают commitment осознанно.
